# Audio position in the URL

## Ask

Rewrite the URL to encode current location of audio of the currently selected movement

## Answer

The URL now has a `t` parameter next to `movement`, holding the audio position in seconds (to the millisecond,
like lyric line times):

```
index.html?movement=anlun-huang/chinese-requiem/ch2&t=83.402
```

How it works (`POSITION IN URL` section in [app.js](../../app.js)):

- **Writing.** Every `timeupdate` (playing, seeking, clicking a lyric line, ±15 s, progress bar, arrow keys) calls
  `updateTimeInUrl()`, which rewrites `t` with `history.replaceState`. Browsers limit how often `replaceState` may be called
  (Safari throws after 100 calls in 30 s), so it writes at most once a second; a change within that second is written when the
  second ends, so the last position is always kept. At 0 the parameter is removed.
- **Reading.** On load, if the `movement` parameter names a movement, `t` is applied once that movement's audio
  metadata has loaded (`loadedmetadata`), capped at the audio's duration. Until then the URL keeps `t` as given. A `t` that isn't
  a number above 0 is removed. `t` without `movement`, or with an unknown movement, is ignored and removed.
- **Selecting another movement** (tree, Prev/Next, auto-advance at the end) removes `t`.
- `setMovementInUrl()` now shares `rewriteUrlParams()` with the position writer; other parameters are kept as before.

README: added a `t` row to the URL parameters table.

Tested in headless Chrome (http-server with Range support):

| Case | Result |
|---|---|
| `?movement=…/ch2&t=12.466` | seeks to 12.466, line 2 highlighted, URL unchanged |
| Play 3.5 s | URL rewritten once a second (`t=12.673`, `13.671`, `14.667`, `15.676`), then `15.966` on pause |
| Reload | resumes at 15.966 |
| 50 seeks in 1 s | 2 `replaceState` calls, URL ends at `t=50` |
| Next movement | `t` removed |
| `?highlight-mode=manual&t=30` | first movement at 0, `t` removed, `highlight-mode` kept |
| `?movement=nope/x/y&t=30` | first movement at 0, `t` removed |
| `t=abc`, `t=-5` | starts at 0, `t` removed |
| `t=99999` | seeks to the end, paused, no auto-advance |

## Ask

The value of the t query parameter should round down to second

## Answer

`updateTimeInUrl()` now writes `Math.floor(audio.currentTime)`, so the URL reads e.g. `t=83`. The app.js comments and the
README `t` row say "whole seconds (rounded down)".

Reading still accepts decimals: `t=12.466` starts at 12.466, and the URL then becomes `t=12`.

Rerun in headless Chrome: playing writes `t=12`, `13`, `14`, `15`; reload resumes at 15; 50 seeks in 1 s give 2
`replaceState` calls, ending at `t=50`; `t=99999` becomes `t=573`; the other cases are unchanged.

Side effect: a lyric line usually starts partway through a second (e.g. 12.466), so a link made right after clicking a line
opens up to a second before it, with the previous line highlighted until playback reaches it.
